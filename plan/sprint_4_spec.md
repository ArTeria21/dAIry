# Sprint 4 — Редактирование заметок: write-API на стороне бота + EDIT в вебе

## Цель

Из Reader и NotePanel можно исправить текст заметки (ошибки транскрибации): правка попадает в
vault, коммитится в git и автоматически пере-обогащается существующим watchdog-ом. Layer3 при
этом **не пишет в vault напрямую** — запись идёт через новый внутренний HTTP-API контейнера бота.

## Контекст (см. fable_report.md P0-2)

- Бот уже владеет всей механикой записи: `journal_lock` (сериализация доступа к vault),
  `git_sync` (pull → commit → push), watchdog пере-обогащения по `content_hash` из
  `note_entry_state` (ручные правки старых заметок — уже поддерживаемый сценарий, см. README).
- После спринта 1 подпись кэша карты включает `content_hash` → пере-обогащение инвалидирует карту.
- После спринта 3 существуют Reader и `/api/days/{date}`.
- Канонический «текст заметки» уже определён поведением `vault_reader.extract_note_raw_text`:
  тело блока без управляемого enrichment-блока, trimmed. Это определение — основа optimistic lock.
- Бот — aiogram-приложение (asyncio, поллинг); aiohttp уже в зависимостях (транзитивно от aiogram).

## Scope

### In scope
1. Бот: внутренний HTTP-сервер (aiohttp) с одним эндпоинтом замены текста заметки; shared-secret
   авторизация; доступен только в docker-сети.
2. Layer3 backend: `PUT /api/notes/{id}` — валидация + проксирование в бот; `raw_text_sha256` в
   ответах `GET /api/notes/{id}` и `/api/days/{date}`.
3. Frontend: режим EDIT в NotePanel и в блоке заметки Reader (textarea, SAVE/CANCEL, обработка
   конфликта).
4. Docker-compose + `.env.example`: секрет, внутренний порт, url.
5. Тесты всех трёх слоёв.

### Out of scope
- Редактирование day summary, frontmatter, тегов, настроения — только текст заметки.
- Создание и удаление заметок из веба.
- Мгновенное пере-обогащение после правки (ждём watchdog; UI честно показывает, что enrichment
  обновится позже).
- История версий правок (git и так хранит).
- Конфликт-резолюшн сложнее optimistic lock.

## Ключевые архитектурные решения

**АР-1. Write-API живёт в контейнере бота** (`src/dairy_bot/services/edit_api.py` + запуск в
`bot.py` рядом с поллингом):
```
POST /internal/notes/replace-text
Headers: X-Edit-Token: <EDIT_API_TOKEN>
Body: { "note_id": "2026-06-08T21:23",
        "note_path": "2026/06/2026-06-08.md",
        "expected_sha256": "<sha256 канонического текущего текста>",
        "new_text": "<новый текст>" }
→ 200 { "new_sha256": ... } | 401 | 404 | 409 (hash mismatch) | 422
```
- aiohttp `web.Application` на `0.0.0.0:8081` **без публикации порта на хост** (только docker-сеть).
- Если `EDIT_API_TOKEN` не задан в env — сервер не стартует вовсе (фича выключена по умолчанию).
- Сравнение токена — constant-time (`hmac.compare_digest`).

**АР-2. Алгоритм замены (внутри `journal_lock`, как все записи бота):**
1. `git_sync.pull()` при `GIT_ENABLED` (той же функцией, что использует сохранение заметок).
2. Прочитать файл; найти блок по `note_id`: распарсить все `## `-заголовки тем же
   `NOTE_HEADING_RE`, восстановить id-последовательность той же логикой, что enrichment
   (`YYYY-MM-DDTHH:MM` + `#n` для дубликатов), найти точное совпадение. Нет совпадения → 404.
3. Вычислить канонический текущий текст блока (тело без enrichment-блока, trimmed — реализация,
   эквивалентная `vault_reader.extract_note_raw_text`; вынести в функцию с юнит-тестом).
   `sha256 != expected_sha256` → 409, файл не трогаем.
4. Собрать новый блок: исходная строка заголовка (байт-в-байт) + пустая строка + `new_text`
   (trimmed) + пустая строка + управляемый enrichment-блок в исходном виде (если был).
   Всё вне блока (frontmatter, соседние блоки, навигация) — байт-в-байт без изменений.
5. Записать файл; `git_sync` commit (`web edit: {note_id}`) + push при `GIT_ENABLED`.
6. Вернуть `new_sha256` (канонический хеш нового текста).

Дальше ничего не делать: watchdog при следующем проходе увидит изменение `content_hash` и сам
пере-обогатит заметку и день (существующий, уже протестированный путь).

**АР-3. Валидация `new_text` (и в боте, и в layer3):**
- Непустой после trim; ≤ 50 000 символов.
- **Ни одна строка не матчится `NOTE_HEADING_RE`** и не начинается с `## ` — иначе правка
  породила бы фантомные блоки и сломала парсинг/enrichment. Нарушение → 422 с человекочитаемым
  сообщением (`"text must not contain note headings (## HH:MM)"`).
- Строки `---` в начале текста не запрещаем (frontmatter ломается только в позиции 0 файла, куда
  текст блока не попадает).
- Маркер `<!-- dairy:note-enrichment -->` в тексте → 422 (защита управляемого блока).

**АР-4. Layer3 `PUT /api/notes/{id}`:**
```
PUT /api/notes/{id}   Body: { "new_text": ..., "expected_sha256": ... }
→ 200 { "id", "new_sha256" } | 401 | 404 | 409 | 422 | 502 (бот недоступен/фича выключена)
```
- Auth как у всех (G3). Note_path берётся из БД по id (клиент его не передаёт и не выбирает —
  защита от path-инъекций).
- Прокси в бот по `BOT_EDIT_API_URL` (env, например `http://dairy-bot:8081`) через `httpx`,
  таймаут 30 с. `EDIT_API_TOKEN` — общий секрет из env.
- Если `BOT_EDIT_API_URL`/`EDIT_API_TOKEN` не заданы → 502 с сообщением "editing disabled"
  (фронт покажет это состояние).
- `GET /api/notes/{id}` и `/api/days/{date}` дополняются полем `raw_text_sha256` (канонический
  хеш) — клиент отправляет его как `expected_sha256`.

**АР-5. Frontend.**
- NotePanel и блок заметки в Reader получают кнопку `EDIT` (ghost, mono). Режим редактирования:
  serif-textarea с текущим `raw_text` (2px радиус, hairline), кнопки `SAVE` (dark filled) /
  `CANCEL` (ghost). Orange не используется (G9: orange занят активными элементами навигации/легенд).
- SAVE → `PUT /api/notes/{id}`; success → выход из режима, refetch заметки/дня, mono-подпись
  `SAVED · ENRICHMENT WILL UPDATE LATER` рядом с чипами mood/topics (исчезает при следующем рендере
  свежих данных).
- 409 → сообщение `NOTE CHANGED ELSEWHERE — RELOADED`, refetch, textarea заполняется свежим
  текстом, правка пользователя сохраняется в буфере компонента (не теряется молча: показать её
  ниже как `YOUR UNSAVED VERSION` в read-only блоке — простое решение без merge).
- 502 → `EDITING DISABLED`.
- Общий компонент редактора один (`web/frontend/src/journal/NoteEditor.tsx`), используется в
  обоих местах.

**АР-6. Docker/конфигурация.**
- `docker-compose.yml`: у `dairy-bot` появляется env `EDIT_API_TOKEN` (из `.env`), порт 8081
  **не** публикуется на хост; `layer3-backend` получает `BOT_EDIT_API_URL=http://dairy-bot:8081`
  и тот же `EDIT_API_TOKEN`. Убедиться, что оба сервиса в одной сети compose.
- `.env.example`: `EDIT_API_TOKEN=` (пустой = выключено) + комментарий, как сгенерировать
  (`openssl rand -hex 32`).
- README: короткий раздел «Editing from the web» (5–10 строк).

## Инварианты спринта

- S4-1. Layer3 не открывает файлы vault на запись и не приобретает rw-mount; единственный путь
  записи — HTTP в бот. Mount vault в layer3 остаётся `:ro`.
- S4-2. Вся запись в vault на стороне бота — только под `journal_lock` и только через шаг 2–5 АР-2.
- S4-3. Заголовок блока и управляемый enrichment-блок после правки байтово сохранены (заголовок —
  идентичен; enrichment-блок — идентичен и стоит после нового текста). Frontmatter и чужие блоки
  не изменяются ни на байт.
- S4-4. Без валидного `X-Edit-Token` — 401; сервер не поднимается без настроенного токена.
- S4-5. Optimistic lock обязателен: запись без совпадения `expected_sha256` невозможна.
- S4-6. Никаких прямых записей в `enrichment.sqlite3` (пере-обогащение — только естественным
  watchdog-путём).
- S4-7. `raw_text_sha256` считается по тому же каноническому тексту на обоих концах (общее
  определение зафиксировано юнит-тестами с одинаковыми фикстурами в боте и layer3).

## Edge cases и ожидаемое поведение

| # | Кейс | Ожидаемое поведение |
|---|---|---|
| E1 | Конкурентная правка: hash устарел | 409, файл не изменён; фронт перезагружает и показывает обе версии (АР-5) |
| E2 | Бот дописал новую заметку в тот же файл между GET и PUT | Хеш редактируемого блока не изменился → правка проходит; чужие блоки не тронуты (тест) |
| E3 | `new_text` содержит строку `## 12:34` | 422 на layer3 (и дублирующая проверка в боте) |
| E4 | `new_text` содержит маркер enrichment-блока | 422 |
| E5 | `new_text` пустой/пробельный | 422 |
| E6 | note_id не найден в файле (файл руками переписали) | 404 от бота → 404 наружу |
| E7 | Файл отсутствует | 404 |
| E8 | git push упал (нет сети) | Файл записан и закоммичен локально → 200 + warning в лог бота; push уйдёт со следующим sync. Поведение зафиксировать тестом с фейковым git_sync |
| E9 | git pull принёс изменение этого же блока | pull выполняется до чтения файла (шаг 1) → хеш сверяется уже с новой версией → корректный 409 |
| E10 | `EDIT_API_TOKEN` не задан | Сервер бота не стартует; PUT → 502 "editing disabled"; кнопка EDIT показывает состояние disabled после первой неудачи |
| E11 | Правка блока с постфактум-заголовком `## June 16 21:55` | Заголовок сохранён байт-в-байт |
| E12 | Правка последнего блока файла (нет следующего `##`) | Граница блока — EOF; файл заканчивается переводом строки |
| E13 | Неверный токен | 401, тело без деталей |
| E14 | Таймаут бота (> 30 с) | 502 наружу, файл может быть записан — фронт по refetch увидит фактическое состояние |

## Критерии приёмки

- **AC-1.** Юнит-тесты замены блока (бот): байтовая сохранность заголовка, enrichment-блока,
  frontmatter и соседних блоков (E2, E11, E12); идемпотентность канонического хеша (S4-7).
- **AC-2.** Интеграционный тест aiohttp-эндпоинта: happy path, 401 (E13), 404 (E6, E7), 409 (E1),
  422 (E3–E5); файл не изменён во всех ошибочных случаях.
- **AC-3.** Тест: после успешной правки существующий механизм отслеживания изменений видит новый
  `content_hash` (прогнать соответствующую функцию watchdog-слоя на изменённом файле — она должна
  пометить заметку изменённой).
- **AC-4.** Layer3-тесты `PUT /api/notes/{id}` с фейковым бот-сервером: маппинг статусов
  (200/404/409/422/502), auth, note_path берётся из БД, а не из запроса.
- **AC-5.** `GET /api/notes/{id}` и `/api/days/{date}` содержат `raw_text_sha256`, совпадающий с
  канонической функцией.
- **AC-6.** Frontend-тесты: EDIT → textarea с текстом; SAVE вызывает PUT с `expected_sha256`;
  409-сценарий показывает свежий текст + несохранённую версию пользователя; 502 → EDITING DISABLED.
- **AC-7.** Все тестовые наборы (бот, web backend, frontend) зелёные; `docker compose config`
  валиден (проверить локально командой).
